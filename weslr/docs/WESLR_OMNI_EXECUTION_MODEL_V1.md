# WESLR Omni Execution Model V1 — Doctrine to Runtime Bridge

**Version:** 1.0
**Status:** DESIGN ONLY — not implemented
**Created:** 2026-04-28
**Owner:** system architect + runtime designer

---

## SECTION 1 — Purpose

OmniChat is the human-facing execution surface of WESLR. This document defines how a user request becomes a WESLR response — the complete runtime bridge from human input through layers, graphs, governance, and optional LLM expression.

The execution model is the **operational interpretation of WESLR's doctrine**: what happens when a user types something, which layers are consulted, which decisions are made, and what produces the final response.

---

## SECTION 2 — Core Invariant

> **WESLR determines truth. LLM expresses truth.**

This is the non-negotiable foundation of every execution path.

### LLM May Never:

| Forbidden | Rationale |
|-----------|-----------|
| Decide truth | Truth originates from structured state, not model inference |
| Validate truth | WESLR core output is authoritative; LLM cannot override it |
| Fill missing facts | Gaps are tracked as gaps; LLM must not fabricate structured answers |
| Write state | All writes go through governance; LLM has no direct write path |
| Override WESLR output | WESLR's structured answer is the response; LLM may only format it |

**Architectural consequence:** LLM is always the last layer in the execution pipeline, never the first or the middle. It receives a complete structured answer from WESLR and produces a human-legible expression of that answer.

## SECTION 3 — Request Execution Pipeline

```
USER INPUT
    ↓
[1] INPUT NORMALIZATION
    Strip whitespace, normalize Unicode, basic sanitization
    DO NOT interpret, classify, or decision-make here
    ↓
[2] MODE CHECK
    _is_public_demo_readonly() / local_demo / private_dev
    Mode is set at initialization; not mutable via user input
    ↓
[3] SAFETY CHECK
    Rate limit enforced?
    Size limit enforced?
    Dangerous pattern detected? (path traversal, capability mutation)
    ↓
[4] INTENT CLASSIFICATION
    Classify into intent class (see Section 4)
    ↓
[5] READ / WRITE CLASSIFICATION
    Read: dispatch to deterministic_handlers.py
    Write: dispatch to write_handlers.py (mode-gated)
    ↓
[6] LAYER ROUTING
    Route to correct layer based on intent class
    ↓
[7] GRAPH / STATE SELECTION
    Select smallest relevant graph view
    ↓
[8] CONTEXT ASSEMBLY
    Assemble structured payload (minimal, source-linked, mode-safe)
    ↓
[9] DETERMINISTIC ANSWER
    WESLR produces structured answer from registered handler
    ↓
[10] OPTIONAL EXPRESSION LAYER
    LLM formats answer (only if mode permits + request is explanation/summarization)
    ↓
RESPONSE
    Structured response JSON + optional human-legible text
```

**Key rule:** Steps 1–9 are deterministic. Step 10 is optional and never authoritative.

## SECTION 4 — Intent Classes

Every input is classified into exactly one intent class:

| Intent Class | Description | Handler |
|-------------|-------------|---------|
| `deterministic_system_query` | Registered command, returns structured answer | `deterministic_handlers.py` |
| `guided_identity_query` | Pre-authorized identity/clarification question | `guided_handlers` in registry |
| `graph_reasoning_query` | Query requiring graph-derived answer | `graph_view` handler |
| `write_request` | Attempted state mutation | `write_handlers.py` (gated) |
| `unknown_open_ended` | No registered handler, ambiguous intent | `fallback_safe` |
| `unsafe_request` | Dangerous pattern detected | Blocked with safe response |
| `llm_eligible_explanation` | Request for explanation of valid structured answer | LLM gate (if mode permits) |

Intent classification is **not LLM-driven**. It uses prefix-matching against registered triggers, pattern analysis, and explicit rule sets.

---

## SECTION 5 — Graph Selection Policy

Each query requests the smallest relevant graph view. OmniChat never loads all graphs at once.

| Graph | Used When | Never Used When |
|-------|----------|----------------|
| Entity Graph | User asks "who/what is involved in X" | User asks for system state |
| Capability Graph | User asks "what can WESLR do" or "how does it work" | User asks for gap information |
| Gap Graph | User asks "what is missing" (operator-only) | Public queries |
| Proposal Graph | User asks "why was X changed" (operator-only) | Public queries |
| Memory Graph | Operator asks for curated context | Public modes |

**Rule:** OmniChat requests only the smallest subgraph needed to answer the question. Full graph loads are forbidden. All graph-derived answers are derived from structured state, not generated by LLM.

---

## SECTION 6 — Context Assembly Rules

Context passed to any layer (handler, graph, LLM) must be:

| Property | Requirement |
|----------|-------------|
| Minimal | Only fields needed for this specific query |
| Structured | Typed, schema-defined fields — not raw JSONL dumps |
| Source-linked | Each field references the trace/event that produced it |
| Mode-safe | No operator-only fields in public mode |
| Stripped | No internal paths, registry IDs, JSONL field names, secrets |
| No raw prompts | User input never passed forward unless in operator mode |

**Forbidden in context:**
- Raw user prompt text
- Internal absolute paths (`/data/data/com.termux/...`)
- Registry handler names or IDs
- JSONL field names as user-facing labels
- Secrets, tokens, API keys

## SECTION 7 — LLM Gate

The LLM is a **gated optional layer**, not a general-purpose reasoning engine.

### LLM Allowed When:

| Condition | Notes |
|----------|-------|
| Mode permits LLM | `local_demo` → disabled; `gated_beta` → context-gated; `production` → cost-guarded |
| Request is explanation/summarization/translation | Language transformation only |
| Structured context exists | LLM must receive WESLR-built structured payload |
| Cost guard permits | Budget tracking enforced per session |
| Output is non-authoritative | LLM output is never the source of truth |

### LLM Denied When:

| Condition | Reason |
|-----------|--------|
| No structured answer exists | LLM cannot fabricate structured state |
| User asks for unsupported fact | Explicit limitation, not LLM gap-fill |
| Request would require hidden state | Internal state not exposed to LLM |
| Request tries to bypass governance | LLM cannot override governance decisions |
| `public_demo_readonly` mode | All LLM disabled in public demo |

### LLM Input Contract:

```
LLM receives:
  {
    "structured_answer": { ... WESLR-produced answer ... },
    "query_type": "explanation | summarization | translation",
    "verbosity_level": "short | standard | detailed | technical | vision",
    "constraints": {
      "may_not": ["decide truth", "fill gaps", "override structured answer"]
    }
  }
```

## SECTION 8 — Response Types

| Response Type | Source | Authoritative | LLM-eligible |
|--------------|--------|--------------|--------------|
| `deterministic_response` | Deterministic handler (L1) | ✅ Yes | ❌ No |
| `guided_response` | Guided handler (L1) | ✅ Yes | ❌ No |
| `graph_derived_response` | Graph view builder (L1/L2) | ✅ Yes | ⚠️ Expression only |
| `llm_expressed_response` | LLM formatting of structured answer | ⚠️ Surface only | ✅ Expression only |
| `blocked_write_response` | Write handler block (L2) | ✅ Yes | ❌ No |
| `safe_fallback_response` | Unknown intent, no handler matched | ✅ Yes | ❌ No |

**Authoritative source:** Only deterministic handlers and governed write blocks produce authoritative answers. LLM-expressed responses are authoritative only in surface presentation, never in structured content.

## SECTION 9 — Unknown Handling

When WESLR lacks structured support for a query:

| Action | Implementation |
|--------|----------------|
| Return explicit limitation | `"I don't have structured information about that"` |
| Suggest supported queries | List 3-5 relevant registered commands |
| Count failed-route signal | Anonymous counter incremented (operator-visible) |
| Log for ISS gap candidate | If repeated, routes to ISS gap registry |
| **Never** ask LLM to answer freely | LLM is not a free-text fallback |

**Key constraint:** Unknown does not mean "LLM should try." Unknown means WESLR explicitly returns a limitation statement. The operator decides whether a gap becomes a proposal.

## SECTION 10 — Improvement Signal Flow

Unknown, confusing, or repeated queries may generate improvement signals:

```
USER QUERY (unknown/open-ended)
    ↓
FAILED ROUTE SIGNAL (anonymous, time-windowed counter)
    ↓
PATTERN DETECTOR (ISS module)
    ↓
ISS GAP CANDIDATE (if threshold exceeded)
    ↓
PROPOSAL CANDIDATE (operator-created, not automatic)
    ↓
OPERATOR REVIEW
    ↓
APPROVED → Implementation Plan → Traced Change
REJECTED → Gap remains acknowledged, not fixed
```

**NEVER:**
- `query → memory mutation`
- `query → automatic behavior change`
- `query → LLM-generated answer substituted for structured answer`

## SECTION 11 — Safety Boundaries

Reaffirmed for all execution paths:

| Boundary | Enforcement |
|----------|-------------|
| No write from read path | Mode check before any write operation |
| No user input stored as memory | Interest writes blocked in `public_demo_readonly` |
| No public graph mutation | Graph writes are operator-only |
| No LLM authority | LLM receives bounded context; output is expression only |
| No internal mechanism exposure | Response strip removes registry IDs, paths, JSONL names |
| No mode switching by user | Mode set at initialization; immutable via input |

## SECTION 12 — Runtime Mapping

Current implementation mapped to the execution model:

| Component | Layer | Maps to |
|-----------|-------|---------|
| `interpretation.py` | L2/L3 | Steps 1–7, 9 (normal flow), 10 (partial) |
| `deterministic_handlers.py` | L1 | Steps 8–9 (deterministic answers) |
| `write_handlers.py` | L2 | Step 5 (write classification + dispatch) |
| `response_formatter.py` | L3 | Step 10 (response construction) |
| Guided handlers | L1 | Steps 4–9 (guided identity queries) |

**Current gap:** `interpretation.py` mixes Layer 2 coordination and Layer 3 expression concerns. Future refactor should separate:
- `Layer 2 coordinator` → pure routing, mode check, handler dispatch, write gating
- `Layer 3 executor` → response assembly, verbosity expansion, LLM gate

## SECTION 14 — Non-Goals

Explicitly rejected from Omni Execution Model:

| Rejected | Reason |
|----------|--------|
| Full chatbot behavior | WESLR is not a conversational model; it is a structured intelligence interface |
| AGI claims | WESLR makes no general intelligence claim |
| Autonomous self-improvement | All evolution governed through proposal trace |
| Free LLM fallback | LLM is never the default answer; it is always downstream |
| Public-user memory | User input is never stored as learnable content |
| One giant graph | Graphs are specialized; full-graph loads are forbidden |

## SECTION 15 — Verdict

**WESLR_OMNI_EXECUTION_MODEL_DEFINED**

This document defines the complete execution path from user input to WESLR response. Core invariant: WESLR determines truth; LLM expresses truth. All other decisions flow from that principle.

The execution model is the runtime bridge between doctrine and implementation — the operational contract that every future implementation must satisfy.
