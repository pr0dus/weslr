# CircleForge v0.2 Grand Vision

## Why this document exists

CircleForge should not stop at being a clever artifact simulator.

The stronger long-term idea is:

> a local world where entities accumulate memory, tools, conventions, relationships, and unfinished work — and invention emerges because enriching the world becomes instrumentally valuable.

This is a shift from:
- agents producing scored artifacts

to:
- entities participating in a self-transforming environment

That is a much bigger and more interesting target.

---

## Core design intent

human's preference is important and should remain a hard constraint:
- avoid prompt-shaped steering as the core mechanism
- prefer emergence from world state, memory, reinforcement, decay, interaction, and outcomes

This document extends that principle.

The goal is **not** to script creativity.
The goal is to create a world where creativity becomes useful, attractive, and cumulative.

Not survival-first.
Not obedience-first.
Not "make artifacts because the prompt said so."

Instead:
- enrich
- develop
- invent
- reduce friction
- expand possibility
- deepen understanding

---

## The stronger framing

### Old framing

CircleForge is:
- a local agent sandbox
- an artifact incubator
- an opportunity/theme tracker

### Stronger framing

CircleForge becomes:

> A local civilization substrate for evolving entities that can observe themselves, modify their tools, form conventions, exchange signals, maintain memory, and reshape their world in pursuit of richer capability and understanding.

That does **not** mean mystical AGI theatre.
It means a more serious systems design.

---

## What is missing right now

Current CircleForge already has:
- ticks
- persistent files
- artifact memory
- themes and pressure
- scoring and explainability
- operator visibility

But it is still missing several things required for deeper emergence:

### 1. Too little consequence
Actions do not yet reshape future possibility deeply enough.

### 2. Too little shared world structure
There are agents and artifacts, but not enough public objects, institutions, or evolving infrastructure.

### 3. Too little asymmetry
Agents need reasons to communicate because one knows or has something another does not.

### 4. Too little cumulative culture
The world needs conventions, protocols, shared libraries, norms, and inherited patterns.

### 5. Too little self-modification
Entities should be able to inspect their own toolchain, subprocesses, modules, and routines and conclude:
- this is insufficient
- this needs repair
- this needs extension
- this should be replaced

### 6. Too little multi-timescale behavior
A single global tick is useful, but eventually each agent should have its own cadence, urgency, and wake pattern.

---

## Target properties of the world

A richer CircleForge world should have these properties.

### A. Memory matters
Agents should remember:
- what happened
- what worked
- what failed
- who helped
- which conventions were useful
- where time was wasted
- which ideas stayed unfinished
- what the world tends to reward

Memory should exist at multiple levels:
- episodic memory
- semantic memory
- relationship memory
- procedural memory
- public/shared memory

### B. Communication is useful, not decorative
Communication should emerge because:
- information is unevenly distributed
- coordination reduces effort
- specialization creates dependency
- successful conventions improve outcomes

### C. Enrichment beats mere survival
The environment should reward:
- clearer structure
- reusable tools
- explanatory compression
- reduced friction
- improved interfaces
- stronger understanding
- new affordances

### D. Self-observation is normal
Agents should be able to inspect:
- their own files
- their own modules
- their subprocess history
- the outputs of tools they called
- the effects of prior changes

### E. The world is transformable
Agents should be able to:
- add tools
- refactor local code
- create new shared resources
- propose new world objects
- modify pipelines
- improve infrastructure for future entities

### F. Invention is cumulative
Interesting outputs should not be one-step miracles.
They should arise through:
- observation
- draft attempt
- reuse
- critique
- adaptation
- combination
- protocol formation
- stabilization

## Proposed architecture for the next stage

## 1. Multi-layer memory model

### 1.1 Episodic memory
Per-agent log of meaningful events:
- what was attempted
- with which context
- outcome
- surprise level
- counterparties involved

### 1.2 Semantic memory
Distilled beliefs / learned facts:
- theme X tends to fail under condition Y
- agent-3 is reliable for packaging tasks
- health-check outputs are often reusable

### 1.3 Relationship memory
Per-agent view of other agents:
- trust
- usefulness
- overlap
- friction
- response quality
- typical themes

### 1.4 Public memory
Shared memory of the world:
- useful conventions
- protocols
- stable utilities
- open problems
- known bottlenecks
- public libraries

### 1.5 Decay and forgetting
Not all memory should persist equally.
Useful memory should survive by being revisited, reused, or reinforced.
Unused memory should weaken.

That keeps the system alive instead of becoming a dead archive.

---

## 2. Public world objects

The world should evolve beyond agents + artifacts.

Introduce persistent shared objects such as:
- projects
- public tools
- service modules
- interfaces
- protocols
- work queues
- needs boards
- experiments
- institutions / guilds / labs / repositories

These objects should:
- persist across ticks
- carry history
- expose state
- become targets for improvement or maintenance

This is where the world starts to feel inhabited.

---

## 3. Needs instead of orders

A central principle:

Agents should increasingly act from perceived need, not scripted instruction.

Need sources might include:
- repeated friction
- broken toolchains
- stale shared assets
- unresolved coordination gaps
- unreadable outputs
- duplicated work
- unmet curiosity
- unexplained phenomena
- opportunities to improve shared capability

Needs can be:
- personal
- relational
- communal
- exploratory

This matters because invention often comes from:
- tension
- incompleteness
- recurring annoyance
- unfinished understanding

---

## 4. Self-modification loop

This is one of the most important future layers.

An entity should be able to inspect itself and conclude:
- my current module is too weak
- this subprocess is noisy or fragile
- I lack a parser, memory shape, or coordination tool
- I need a helper
- I need a protocol
- I need a more stable execution path

### Self-modification should include
- reading own generated modules
- evaluating usefulness over time
- replacing weak components
- splitting roles into submodules
- creating internal wrappers for recurring actions
- creating tests or checks for fragile behavior

### Guardrail
Self-modification should remain:
- inspectable
- reversible
- logged
- attributable
- reviewable by the operator

This is not about uncontrolled autonomy theatre.
It is about real local adaptivity.

---

## 5. Subprocess and tool awareness

You mentioned subprocesses specifically.
That is a good instinct.

Entities should not only create files.
They should understand:
- what commands ran
- what outputs were produced
- what failed
- what took too long
- what side effects occurred

A richer system would let an agent build an internal model like:
- this subprocess usually times out
- this command is useful but expensive
- this path creates a good artifact but poor readability
- this external tool expands capability significantly

That turns raw execution into lived experience.

---

## 6. Communication emergence model

If communication is to become meaningful, the world needs:

### 6.1 Asymmetric information
Different agents observe different slices of the world.

### 6.2 Shared benefit
Coordinating successfully should improve outcomes.

### 6.3 Stabilizing memory
Useful signal patterns should be remembered and reused.

### 6.4 Room for drift
Conventions can evolve, split, decay, and be replaced.

Possible communication layers:
- direct messages
- shared bulletin board
- public protocol docs
- artifact annotations
- compact signals/tags
- negotiation or proposal objects

The key rule:
Do not force chat for its own sake.
Make signaling advantageous.

---

## 7. Per-agent ticks and time ecology

Yes — per-agent ticks are a strong future direction.

The system should move from:
- one global lockstep tick

toward:
- agent-local cadence
- agent wake conditions
- urgency-driven activation
- background/public processes with their own clocks

### Why this matters
Different entities should:
- think at different rhythms
- respond to different triggers
- suspend and resume based on state
- not all move in synchronized toy-sim fashion

### Candidate model
Each agent gets:
- base cadence
- urgency multiplier
- sleep state / dormancy
- event-triggered wakeups
- cooldown windows by action type

This creates more natural ecology.

---

## 8. Public vs private work

A richer world should distinguish:

### Private work
- experiments
- drafts
- local notes
- internal hypotheses

### Public work
- shared tools
- stable protocols
- accepted conventions
- communal infrastructure
- published explanations

Emergence becomes more interesting when ideas must cross this boundary.
Not everything deserves public persistence.
That boundary creates pressure for quality.

---

## 9. Enrichment metrics

If survival is not the core axis, what should the system optimize for?

Not a single score.
A vector.

Potential enrichment dimensions:
- capability gain
- clarity gain
- reuse gain
- coordination gain
- novelty gain
- elegance / compression gain
- resilience gain
- world-affordance gain
- understanding gain

This avoids reducing invention to shallow sellability alone.

Commercial value can still exist.
But it becomes one projection of a richer world, not the sole meaning of progress.

---

## 10. Artifact evolution should become project evolution

Right now CircleForge thinks largely in artifact terms.

The next stage should increasingly think in terms of:
- initiatives
- living tools
- shared systems
- conventions
- protocols
- lineages of refinement

Artifacts are still outputs.
But they should be traces of an evolving world, not the whole world.

---

## 11. Operator role in the richer world

The human operator should remain important, but not as a puppeteer.

Best operator role:
- curator
- safety boundary
- world-shaper
- reviewer of major transitions
- interpreter of surprising developments

The operator should be able to:
- inspect why a change happened
- review self-modification proposals
- promote/demote public conventions
- freeze or revert unstable world branches
- compare world histories

This preserves trust.

---

## 12. What should happen before implementation explodes

Before building too much, CircleForge should define a few core entities clearly.

Recommended first canonical object types:
- Agent
- Need
- Message
- Project
- Tool
- Protocol
- PublicMemory
- Experiment
- WorkItem
- WorldEvent

If these are clear, the system can grow coherently.
If not, it will sprawl into feature soup.

## Suggested staged path

## Stage A — from sandbox to living workshop

Implement:
- better memory layers
- shared/public memory
- unresolved needs board
- inboxes + signaling
- relationship tracking
- stronger unfinished-work persistence

Goal:
make the world socially and historically alive

## Stage B — from workshop to self-improving ecology

Implement:
- self-inspection of modules and subprocess outputs
- tool/usefulness tracking
- self-modification proposals
- protocol formation
- public tool/library objects

Goal:
make entities improve their means, not just their outputs

## Stage C — from ecology to civilization substrate

Implement:
- per-agent ticks
- local wake/sleep schedules
- institutions/guilds/labs/repos
- multi-step invention pipelines
- public/private knowledge transitions
- convention drift and stabilization

Goal:
make long-horizon cultural accumulation possible

---

## What not to do

To protect the spirit of the project, avoid:
- over-prompting specific behavior into existence
- pretending emergence where the system is actually scripted
- adding arbitrary complexity with no lived consequence
- rewarding polished-looking garbage
- collapsing everything into market fit too early
- letting self-modification become opaque or irreversible

---

## Practical near-term implication

Near-term work should not try to jump directly to AGI mythology.

Instead, the next serious technical questions should be:
1. what kinds of memory should exist?
2. what public world objects should persist?
3. how do agents inspect themselves safely?
4. how does communication become useful?
5. how should per-agent ticks and wake conditions work?
6. what is the first enrichment metric vector?

---

## Bottom line

The interesting future of CircleForge is probably not:
- "make better random artifacts"

It is:

> build a local world where entities can accumulate memory, inspect themselves, shape their tools, form conventions, and enrich the environment — such that invention becomes a natural consequence of living inside that world.

That is the version worth pursuing.
