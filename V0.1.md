# CircleForge v0.1 Plan

## What v0.1 means

v0.1 should not mean "finished."
It should mean CircleForge has become a coherent, legible, usable early system.

A good v0.1 would mean:
- the internal opportunity loop is coherent
- the dashboard is usable for a human operator
- rollback/version hygiene is reliable
- pack offer workflow exists end-to-end
- explainability is good enough for human judgment
- the project can produce outputs that are at least plausible as reusable micro-tools

## v0.1 checklist

Before declaring v0.1, CircleForge should ideally have:

- stable dashboard with drill-downs
- persistent event log
- artifact and pack explainability split into:
  - internal strength
  - external proof
  - risks
  - next actions
- pack offer workflow with recorded outcomes
- weak-proof reporting
- safe rollback path via backups/tags/releases
- clear README positioning
- at least one or two believable pack families that look externally legible

## What to stop adding

To reach v0.1, CircleForge should avoid feature drift.

Do **not** keep adding internal complexity just because it is interesting.
In particular, avoid:
- more simulation cleverness without stronger reality contact
- vague new subsystems that make the project harder to explain
- too many new scoring layers unless they unlock clearer decisions
- dashboard bloat without better operator actionability
- fake autonomy theater or prompt-shaped steering

Plain version:
- stop adding features that mainly impress the builder
- prioritize features that help a human judge, validate, offer, or operate the system

## What must be fixed before v0.1

These are the most important pre-v0.1 gaps.

### 1. Stronger external proof

CircleForge still generates internal confidence faster than real-world evidence.

That means it needs stronger ways to answer:
- did anyone actually use this?
- did it solve a real problem?
- did someone accept or reject it?
- why was it rejected?
- what changed after revision?

### 2. Stronger product-shaped flows

CircleForge is no longer just a sim, but the path from:
- artifact
- to pack
- to offer
- to outcome

still needs to feel more concrete and product-like.

That means improving:
- offer attempts
- buyer context
- outcome logging
- revision loops
- pack-to-product packaging

### 3. Stronger operator usability

The dashboard is useful, but it is still more of a monitor than a true control surface.

Before v0.1, the project should feel easier to:
- inspect
- understand
- navigate
- act on

That means:
- clearer drill-downs
- better operator actions
- clearer histories and event trails
- less need to inspect raw JSON or guess what to do next

## What can wait until after v0.1

These are valuable, but they should not block v0.1.

- deeper replay/history systems
- more advanced emergence logic
- richer clustering sophistication
- more complex buyer segmentation
- heavier automation around outreach or validation
- more ambitious UI polish
- broader artifact families beyond the strongest practical niches

## What is limiting progress now?

This is the key bottleneck section.

For CircleForge, the current bottleneck is **not**:
- more internal simulation features
- more abstract scoring
- more complexity for its own sake

The real bottlenecks are:

### A. Stronger external proof

Meaning:
CircleForge can already say "this looks promising," but it is still weak at proving:
- someone used it
- someone wanted it
- someone rejected it for a specific reason
- the next revision got better

So progress is limited by lack of real-world evidence.

### B. Stronger product-shaped flows

Meaning:
The project still needs a clearer path from:
- generated thing
- to understandable thing
- to packaged thing
- to offerable thing
- to outcome

Right now, some of that exists, but not yet strongly enough.

### C. Stronger operator usability

Meaning:
A human should be able to look at CircleForge and quickly understand:
- what is happening
- what matters
- what is improving
- what is weak
- what action to take next

If using the system still feels too technical, too hidden, or too scattered, that slows progress.

## In plain human words

If I reduce it brutally:

CircleForge does **not** mainly need more imagination right now.
It needs:
- more proof
- more clarity
- more usability

That is what should dictate the next steps.

## Practical next-step filter

When choosing new work before v0.1, ask:

1. Does this improve real-world proof?
2. Does this make the system easier for a human to operate?
3. Does this make the artifact-to-offer path clearer?
4. Does this reduce ambiguity around what CircleForge actually is?

If the answer is mostly no, the feature is probably not a pre-v0.1 priority.
