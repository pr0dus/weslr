# WESLR Generalized Friction Improvement Process V1

## SECTION 1 — Executive canon

**Canon principle:**
> WESLR improves only when friction is transformed into a generalized, replay-proven, owner-approved cognition update.

Core rules:
- WESLR does **not** learn by uncontrolled neural weight changes.
- WESLR does **not** hardcode individual prompt answers as the improvement strategy.
- WESLR improves through **governed friction abstraction**.
- Existing governance / proposal / CDI / proof surfaces must be reused.
- No parallel self-improvement lifecycle is allowed.
- **ISS** is internal framing only.
- Public wording must stay bounded.

## SECTION 2 — Internal ISS framing vs public wording

Internal ISS meaning:
- **intelligence superstructure / integrated self-sustaining system**
- a working roadmap for continuity, identity awareness, capability awareness, friction-trained growth, replayable proof, governed promotion, and controlled generalization

Why useful internally:
- gives a shared label for the full growth stack
- keeps the roadmap above “chat improvements” only
- reminds us the target is a controlled cognition substrate, not a single surface

Why it must not be public overclaim:
- it can sound like official capability settlement
- it can blur the boundary between internal roadmap and externally validated fact
- it can invite AGI / consciousness / certification claims before evidence exists

Safe public alternatives:
- governed intelligence system
- continuity-first architecture
- evidence-aware system
- operator-approved evolution
- replayable improvement
- controlled general-capability roadmap

Forbidden public wording:
- AGI
- conscious
- sentient
- officially Turing-test ready
- certified intelligence
- benchmark-proven intelligence
- autonomous self-improvement
- self-sustaining public intelligence

## SECTION 4 — Generalized process lifecycle

1. **Observe answer friction**
   - Input: weak / wrong / overly generic answer behavior
   - Output: candidate friction signal
   - Existing modules: response-fit helpers, unknown-engine assimilation
   - Invariants: metadata-only, no raw private data by default
   - Forbidden: model calls, runtime writes, public claims

2. **Capture safe metadata case**
   - Input: friction signal
   - Output: friction case record
   - Existing modules: `weslr/friction_case_capture.py`
   - Invariants: safe prompt descriptor, mismatch labels, no raw prompt storage by default
   - Forbidden: raw transcript capture, state writes, runtime authority

3. **Replay current behavior**
   - Input: captured case set
   - Output: replay results
   - Existing modules: `weslr/friction_replay_harness.py`
   - Invariants: deterministic, no model/provider calls
   - Forbidden: runtime wiring, state mutation

4. **Classify mismatch**
   - Input: replay result
   - Output: mismatch labels / route-family gap labels
   - Existing modules: selector, router, unknown-engine assimilation, response-fit helpers
   - Invariants: fail-closed, metadata-only
   - Forbidden: hidden learning authority

5. **Mine repeated patterns**
   - Input: multiple friction cases / replay outcomes
   - Output: repeated-pattern candidate
   - Future helper: `weslr/friction_pattern_miner.py`
   - Invariants: cluster only, do not apply
   - Forbidden: auto-promotion, behavior mutation

6. **Infer generalized failure pattern**
   - Input: repeated-pattern candidate
   - Output: generalized failure pattern hypothesis
   - Future helper: `friction_pattern_miner.py`
   - Invariants: keep source families visible
   - Forbidden: claim certainty beyond replay evidence

7. **Build update proposal**
   - Input: generalized pattern hypothesis
   - Output: governed proposal packet
   - Existing modules: `weslr/friction_update_proposal_bridge.py`, `weslr/contract_improvement_proposal_bridge.py`, `weslr/cdi_proposal_builder.py`
   - Invariants: operator-reviewable, metadata-only
   - Forbidden: approval grant, auto-apply

8. **Expand replay suite**
   - Input: pattern candidate + original cases
   - Output: replay suite for neighbors/paraphrases/boundaries/controls
   - Future helper: `weslr/friction_replay_suite_builder.py`
   - Invariants: prove generalization and anti-hardcoding
   - Forbidden: store raw private data, inject runtime authority

9. **Owner review**
   - Input: proposal packet + proof evidence
   - Output: approve / deny / defer
   - Existing modules: `weslr/governance_surface.py`, `weslr/change_proposals.py`, `weslr/operator_proposal_review.py`, `weslr/cdi_decision_log.py`
   - Invariants: owner-first, reversible, auditable
   - Forbidden: parallel approval lifecycle

10. **Approved realization**
   - Input: approved proposal
   - Output: approved implementation changes
   - Existing modules: `weslr/proposal_realization.py`
   - Invariants: rollback planning, scoped files, approved only
   - Forbidden: autonomous self-modification

11. **Before/after replay**
   - Input: pre/post realization state
   - Output: replay comparison
   - Existing modules: `weslr/friction_replay_harness.py`
   - Invariants: same suite, comparable results
   - Forbidden: cherry-picked proofing

12. **Anti-hardcoding proof**
   - Input: neighbor / paraphrase / boundary / control cases
   - Output: proof that improvement is generalized
   - Existing tests: selector, renderer, router, replay, starter realization tests
   - Invariants: must include non-exact prompts and controls
   - Forbidden: exact-prompt-only success

13. **Proof report**
   - Input: full before/after evidence
   - Output: standardized internal proof artifact
   - Future helper: `weslr/friction_training_proof_report_run.py`
   - Invariants: include boundaries and protected-file checks
   - Forbidden: certification / public readiness claims

14. **Promotion decision**
   - Input: proof report + owner judgment
   - Output: behavior-pack / core-rule promotion or defer
   - Future helpers: `behavior_pack_registry.py`, `behavior_pack_promotion_policy.py`
   - Invariants: no auto-promotion
   - Forbidden: hidden live router, public claim surface

15. **Regression monitoring**
   - Input: promoted rule / pack / selector change
   - Output: ongoing regression checks
   - Existing modules: replay harness + tests
   - Invariants: monitor drift, keep proof current
   - Forbidden: silent behavior mutation

## SECTION 5 — Friction abstraction levels

- **Level 0:** exact friction instance
- **Level 1:** prompt-family friction
- **Level 2:** answer-shape friction
- **Level 3:** method / case / selector friction
- **Level 4:** behavior-pack friction
- **Level 5:** core cognition rule candidate

Rules:
- Level 0 alone must **not** trigger behavior change.
- Only Level 2+ may justify an implementation proposal.
- Level 4/5 require stronger replay evidence and owner review.
- The more general the claim, the stronger the replay suite must be.
