## 1. Why Fixed Human‑Readable Primitive Lists Are Insufficient

The current BH80 uses 21 human‑written primitive names (13 core + 8 aliases). These cover a small slice of the ARC/grid‑world transformation space. The real transformation space is combinatorially vast:

- **Object selection**: "largest", "leftmost", "colored‑same‑as", "touching‑border", "overlapping", "enclosed‑by" — dozens of selection predicates exist beyond "largest"
- **Transform compositions**: rotate‑then‑crop‑then‑recolor is one chain; the space of 3‑step chains over even 50 primitives is 50³ = 125,000 — far beyond human enumeration
- **Conditional transforms**: "if object has holes, do X; otherwise do Y" — no current primitive expresses conditionality
- **Construction transforms**: "draw a rectangle around the selected object" or "extend the pattern to fill the canvas" — no current primitive constructs new geometry
- **Relational transforms**: "swap the two largest objects" or "align objects by centroid" — no current primitive expresses inter‑object relations

Human‑written primitive names are a ceiling, not a floor. They encode what a human designer thought to name, not what the transformation space contains. To discover new transformations, WESLR needs a native language that can express, compose, and test operators beyond human naming.

## 2. WESLR‑Native Language Freedom

The internal language is **not required to be human‑readable**. It may take any of these forms:

- **Symbolic programs**: S‑expression‑like or stack‑based code with invented tokens
- **Graph rewrites**: pattern‑→replacement rules over grid cell graphs
- **Object‑relation calculus**: first‑order predicates over objects, positions, colors
- **Mask algebra**: boolean operations over binary masks (union, intersection, complement, difference)
- **Transformation lattices**: partially ordered composition graphs with type constraints
- **Compressed operator codes**: fixed‑width binary encodings of operator IDs + parameters
- **Invented tokens**: new vocabulary elements generated by search, not predefined
- **Typed composition graphs**: DAGs where nodes have type signatures and edges respect type compatibility
- **Latent‑but‑serialized rule forms**: learned or discovered patterns serialized as deterministic programs
- **Hybrid symbolic/geometric programs**: mixing discrete logic with continuous parameters (rotation angle, crop threshold)

The only requirement is that the language is **deterministic, executable, and semantically verifiable**. Human readability is explicitly optional.

## 3. Grid‑World Ontology

The bounded world the language operates over:

| Entity | Definition |
|--------|-----------|
| **Grid** | 2D array of integers (colors 0–9), the fundamental unit |
| **Cell** | A single (row, col, value) triple |
| **Color** | Integer 0–9; 0 is default background |
| **Background** | The most common color in the grid, or an explicitly specified value |
| **Object** | A maximal connected component of non‑background cells |
| **Component** | Same as object (connected via 4‑connectivity) |
| **Region** | A subset of cells defined by a mask or bounding box |
| **Mask** | Binary grid (same dimensions) marking selected cells |
| **Border** | Cells at the edge of the grid or at the edge of an object's bounding box |
| **Hole** | Background cells fully enclosed by an object |
| **Bounding box** | Minimal rectangle containing an object: [min_row, min_col, max_row, max_col] |
| **Axis** | Row axis (horizontal) or column axis (vertical) |
| **Relation** | A predicate between two or more objects (left‑of, above, same‑color, overlaps, encloses) |
| **Symmetry** | A transformation that preserves the grid: horizontal flip, vertical flip, 90° rotation, 180° rotation, identity |
| **Repetition** | A periodic pattern in the grid (by row, column, or block) |
| **Pattern** | A deterministic function from position to color |
| **Count** | Integer result of counting objects, cells, or features |
| **Path** | A connected sequence of cells forming a line or curve |
| **Canvas** | The grid as a drawing surface, with size and background |
| **Transformation** | A function Grid → Grid (or Grid → Mask, Grid → Count, etc.) |

## 4. Type and Validity System

Even if the language is alien, it must have strict types:

### 4.1 Core types

| Type | Description |
|------|-------------|
| `Grid` | 2D integer array |
| `Object` | A connected component with metadata (bbox, color, size) |
| `ObjectSet` | A set of objects |
| `Mask` | Binary grid marking selected cells |
| `Region` | A rectangular sub‑area defined by bounding box |
| `Color` | Integer 0–9 |
| `Count` | Non‑negative integer |
| `Relation` | A binary predicate over objects |
| `Transform` | A function Grid → Grid |
| `Pattern` | A function (row, col) → Color |
| `Program` | A composition of transforms (the language expression itself) |
| `Trace` | Execution trace of a program on a grid |
| `Invariant` | A property that holds before and/or after a transform |

### 4.2 Validity rules

1. **Deterministic execution**: Same input → same output, always
2. **Finite evaluation**: Every program terminates in bounded time
3. **No hidden external calls**: No network, no file IO, no provider/model calls
4. **No task‑id shortcuts**: Programs may not access task metadata
5. **No expected‑output leakage**: Programs may not read oracle outputs
6. **No oracle‑trace leakage to solver**: Solver path must not see oracle traces
7. **Type safety**: Operator inputs and outputs must match declared types
8. **Bounded grid size**: Maximum grid dimensions enforced (e.g., 30×30)

## 5. Primitive Invention Mechanism

WESLR proposes new primitive candidates from the native language using:

### 5.1 Composition of existing operators
- Take 2–3 existing primitives and compose them into a new named operator
- Example: `extract` + `rotate` = `extract_rotate` (a new primitive that extracts and rotates in one step)

### 5.2 Mutation of operator graphs
- Take an existing operator's internal graph and mutate:
  - Swap argument order
  - Change a constant (rotation angle, target color)
  - Add/remove a step
  - Replace a sub‑expression with a different operator

### 5.3 Search over relation patterns
- Enumerate binary relations between objects (left‑of, above, same‑color, encloses, overlaps)
- Generate selection rules: "select the object that is leftmost and has the most holes"
- Generate conditional transforms: "if two objects have the same color, merge them"

### 5.4 Generation of object‑selection rules
- Combine predicates: `is_largest AND has_holes AND touches_border`
- Generate negated selections: `NOT is_largest` (select everything except the largest)

### 5.5 Generation of color/shape/geometry/topology transforms
- Color: recolor to a specific value, swap two colors, gradient fill
- Shape: fill holes, remove protrusions, skeletonize
- Geometry: rotate by arbitrary angle, scale by factor, translate by offset
- Topology: merge objects, split object at narrowest point, connect objects with a path

### 5.6 Generation of conditional transforms
- `IF object_count > 2 THEN apply_transform_A ELSE apply_transform_B`
- `IF largest_object_has_holes THEN fill_holes ELSE recolor`

### 5.7 Generation of construction transforms
- Draw a rectangle around the selected object
- Extend a pattern to fill the canvas
- Draw a line connecting two objects' centroids
- Copy an object to a new position

### 5.8 Generation of pattern‑extension transforms
- Detect row‑alternating pattern and extend it
- Detect block repetition and fill missing blocks
- Detect color gradient and continue it

### 5.9 Discovery of reusable subprograms
- From successful task solutions, extract common sub‑sequences
- Promote them as named primitives if they appear in ≥ 3 successful solutions and pass anti‑cheat

## 6. Perspicuity Role

Perspicuity in this context does **not** mean "easy for humans to understand." It means:

| Property | Definition |
|----------|-----------|
| **Internally clear** | The language has well‑defined syntax and semantics |
| **Minimal** | No redundant operators; each has a unique semantic fingerprint |
| **Non‑duplicative** | No two operators produce the same output for all inputs |
| **Reusable** | Operators appear in multiple task solutions, not just one |
| **Compressive** | A short expression captures a transformation that would be verbose in raw grid operations |
| **Falsifiable** | Operators have negative controls that distinguish them from no‑ops |
| **Testable** | Oracle and solver can independently execute the operator |
| **Semantically stable** | Same input always produces same output |
| **Resistant to shortcut solving** | Operators cannot be bypassed by metadata or task‑id |
| **Useful across task families** | Operators generalize beyond their origin task |

## 7. Primitive Contract Schema

Every candidate primitive must expose:

```json
{
  "primitive_id": "<stable_identifier>",
  "internal_expression": "<serialized alien-language program>",
  "content_hash": "<sha256 of internal_expression>",
  "type_signature": {
    "input": "Grid",
    "output": "Grid",
    "parameters": ["angle"]
  },
  "deterministic_semantics": "yes",
  "preconditions": ["grid is non-empty", "grid has at least one non-background cell"],
  "invariants_preserved": ["grid dimensions"],
  "invariants_changed": ["cell colors in selected region"],
  "oracle_execution": "reference_primitive implementation exists",
  "solver_execution": "dispatch wrapper exists",
  "positive_examples": ["example_1", "example_2"],
  "negative_controls": ["no-op variant produces different output"],
  "anti_cheat_checks": ["no task_id access", "no oracle trace access"],
  "regression_tests": ["BH80 still 80/80", "new primitive tests pass"],
  "promotion_criteria": "all checks pass + semantic_exact on positive examples",
  "human_summary": "optional approximate description"
}
```

Human‑language explanation is **optional** and may be approximate.

## 8. Oracle and Solver Relationship

For every promoted primitive:

| Requirement | Rule |
|-------------|------|
| Oracle path | Must execute independently, own implementation, no import of solver dispatch |
| Solver path | Must execute via dispatch wrapper, no import of oracle |
| `semantic_exact` | Must remain grid equality (element‑wise, dimension‑wise) |
| `structural_pass` | Must remain separate from `semantic_exact` |
| Promotion gate | No primitive promoted without oracle/solver agreement on positive tests AND negative controls |

The oracle and solver must **never share execution code**. The oracle implements reference semantics; the solver implements the same semantics through its own dispatch path. The semantic scorer compares outputs.

## 9. Audit Surface for Alien Language

Because the internal language may be unintelligible to humans, these audit artifacts are **mandatory**:

| Artifact | Purpose |
|----------|---------|
| Serialized internal expression | The alien‑language program, serialized as bytes/JSON/S‑expr |
| Content hash | SHA256 of the serialized expression — for identity and provenance |
| Type signature | Input/output types and parameters |
| Deterministic execution trace | Step‑by‑step record of grid state at each sub‑operation |
| Input/output examples | At least 3 input grids with corresponding output grids |
| Oracle output | The oracle's reference output for each example |
| Solver output | The solver's output for each example |
| Grid equality result | `semantic_exact` / `failed` for each example |
| Invariant checks | Which invariants are preserved/changed |
| Negative‑control results | No‑op variant and order‑reversal variant results |
| Regression impact summary | "BH80: 80/80 (no change)" or "BH80: 79/80 (regression — explain)" |
| Optional human summary | Lossy, approximate, natural‑language description (may be omitted) |

The audit surface does **not** require translating the alien language into human prose. It requires proving that the language is semantically correct and safe.

## 10. Candidate Promotion Pipeline

```
generated → typed → executable → oracle_defined → solver_targeted →
tested → anti_cheat_validated → regression_safe → promoted
```

| Stage | Check | Failure action |
|-------|-------|---------------|
| **generated** | Internal expression created | Discard if generation fails |
| **typed** | Type signature valid | Discard if type error |
| **executable** | Runs deterministically on test grids | Discard if crash or non‑deterministic |
| **oracle_defined** | Oracle reference implementation exists | Block promotion — implement oracle first |
| **solver_targeted** | Solver dispatch wrapper exists | Block promotion — implement solver first |
| **tested** | Positive examples: oracle and solver agree | Block — debug mismatch |
| **anti_cheat_validated** | No‑op control, order‑reversal, sentinel all pass | Block — strengthen primitive or discard |
| **regression_safe** | BH80 remains ≥ 72/80 after primitive addition | Block — investigate regression |
| **promoted** | Primitive enters the frozen primitive set with stable ID | ✅ |

**Promotion is blocked unless all checks pass. No exceptions for "almost working" primitives.**

## 11. Task Generation from Native Language

Alien‑language primitives generate tasks:

| Task type | Description |
|-----------|-------------|
| Single primitive probes | Test one new primitive in isolation |
| Two‑step compositions | Compose new primitive with a known primitive |
| Three‑step compositions | Full 3‑step chains (extends BH80 pattern) |
| Rival grammar traps | Tasks designed to defeat simple grammars |
| No‑op traps | Tasks where no‑op chain should produce different output |
| Distractor‑pressure tasks | Multiple objects with visual similarity |
| Boundary‑pressure tasks | Objects touching edges, clipped boundaries |
| Relation‑pressure tasks | Multi‑object relational reasoning required |
| Pattern continuation tasks | Extend a detected pattern |
| Unknown‑family candidates | New synthetic grammars from promoted primitives |

All tasks must pass the same scene materialization, oracle, and semantic scoring pipeline as BH80.

## 12. Regression Policy

BH80 stays frozen:

| Checkpoint | Requirement |
|------------|-------------|
| Before language implementation | BH80 = 80/80 ✅ (current) |
| After language implementation | BH80 = 80/80 (must not change) |
| Before primitive promotion | BH80 = 80/80 |
| After primitive promotion | BH80 ≥ 72/80 (strong gate); ≥ 68/80 (absolute floor) |

- **Below 80/80**: regression requiring written explanation
- **Below 75/80**: preferred expansion gate lost — 120 blocked
- **Below 72/80**: strong gate lost — block all changes
- **Below 68/80**: critical regression — rollback required

## 13. Relationship to 120

The 120‑task expansion should **not** merely be 40 more tasks from the old 21 primitive names. It should be the first semantic expansion that includes:

| Component | Count | Source |
|-----------|-------|--------|
| Frozen BH80 base | 80 | Existing 80 tasks (unchanged) |
| New native‑language tasks | 40 | Generated from promoted native primitives |
| **Total** | **120** | |

### 120‑task composition rules
- Old primitives: included as‑is
- Newly promoted primitives: included with oracle, solver, and anti‑cheat validation
- Candidate (unpromoted) primitives: may appear in tasks but are explicitly marked as `candidate`, not counted as `solved`
- No unvalidated primitive is counted in the semantic score

### 120‑task gates

| Gate | Requirement |
|------|-------------|
| Semantic Minimal | ≥ 102/120 exact (85%) |
| Semantic Strong | ≥ 108/120 exact (90%) |
| Semantic Clean | 120/120 exact (100%) |
