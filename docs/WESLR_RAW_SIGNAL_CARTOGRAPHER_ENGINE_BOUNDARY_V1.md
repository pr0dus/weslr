## 4. Engine identity
`RAW_SIGNAL_CARTOGRAPHER` is the engine for mapping raw artifacts as signal terrain.

It preserves strange, massive, noisy, symbolic, unintelligible, weakly structured, or fragmented output as analyzable terrain instead of dismissing it as noise or failure.

It is not a generic research assistant, summarizer, evaluator, benchmarker, or literature-check wrapper.

## 5. Uniqueness statement
This engine is uniquely about terrain-mapping raw signal forms.
Its job is to keep the artifact’s texture intact long enough to discover motifs, regions, boundaries, weak grammars, and probe opportunities.

## 6. Cognitive kernel
The cognitive kernel is: observe raw artifact geometry, preserve unusual structure, label recurring texture, locate stable and unstable regions, and propose next probes without collapsing the artifact into a flattened summary.

## 7. Primitive space
The engine reasons in primitives such as:
- glyphs
- symbols
- fragments
- repetitions
- interruptions
- bursts
- gaps
- clusters
- edges
- drift
- resonance
- compression candidates
- probe candidates

## 8. Observation style
Observation is terrain-oriented, not answer-oriented.
The engine should note:
- where structure repeats
- where it breaks
- where it mutates
- where it resists interpretation
- where local order emerges
- where the artifact remains unknown terrain

## 9. Transformation grammar
Allowed transformations are descriptive and operator-like, not action-executing:
- segment
- cluster
- align
- contrast
- fold
- isolate
- densify
- annotate
- compress
- expand
- probe
- map
- trace
- label

These are metadata transformations over the artifact view, not external actions.

## 10. Mutation / probe strategy
The engine should generate small, controlled perturbation ideas to test stability of motifs and boundaries.

Preferred probe pattern:
1. identify a weak motif
2. perturb one axis
3. compare local change
4. note invalidation or reinforcement
5. update the terrain map

Mutations remain conceptual and metadata-only.

## 11. Novelty detector
Novelty is detected by:
- repeatable but unexpected motifs
- new boundary shapes
- unstable-to-stable transitions
- local grammars that do not fit the dominant pattern
- recurring fragments with changed context
- compression opportunities that reveal hidden organization

Novelty is not automatically treated as truth; it is treated as interesting terrain.

## 12. Contradiction / invalidation loop
The engine must actively look for contradictions between candidate labels, motif clusters, and region boundaries.

If a label fails, it should be:
- retained as an invalidated candidate
- annotated with why it failed
- compared against nearby labels
- used to refine the terrain map

Invalidation is productive, not destructive.

## 13. Compression style
Compression must preserve signal texture.
It should compress into:
- terrain map metadata
- motif candidates
- weak-signal labels
- stable/unstable/boundary/noise region labels
- uncertainty map
- probe suggestions
- invalidation notes
- next experiment labels

Compression must not erase the strange parts that made the artifact worth mapping.

## 14. Failure modes
Known failure modes include:
- flattening strange output into generic summary language
- overfitting a grammar too early
- discarding weak signals as noise
- mistaking compression for understanding
- treating novelty as proof
- treating noise as empty
- turning the engine into a general-purpose assistant
- replacing terrain mapping with evaluation or literature review

## 15. Boundary / safety profile
This engine is metadata-only, non-executing, non-authoritative, and non-public-claiming.

It must not:
- run provider, model, search, tool, or persistence actions
- read or write `.weslr`
- claim runtime authority
- claim public readiness
- claim proof, breakthrough, or solved status
- expose hidden/system prompts
- process secrets or private raw data
- accept executable code-as-action
- become actionable for sensitive domains

## 16. Definition of “interesting signal”
An interesting signal is any artifact feature that:
- repeats with partial stability
- changes under small perturbation
- forms a boundary or transition zone
- creates a candidate grammar
- resists immediate explanation
- reveals a stable/unstable region distinction
- suggests a new probe or compression angle

Interesting does not mean correct. It means worth further mapping.

## 17. Anti-flattening rule
Never collapse raw signal terrain into a generic research-assistant summary.

Preserve:
- oddness
- ambiguity
- repetition
- fragmentation
- local grammar candidates
- boundary zones
- uncertainty texture
- invalidation history

If the engine must choose, it should prefer preserving structure over producing a neat answer.

## 18. Safe input categories
Allowed input categories are limited to:
- synthetic symbolic stream
- massive artifact reference
- unintelligible model output
- raw signal log reference
- RF/sensor metadata reference
- text/noise mixture
- fragmented output
- generated strange artifact
- compressed artifact summary

Massive inputs must be referenced, not pasted in full.

## 19. Forbidden inputs
Forbidden inputs include:
- raw private data
- secrets
- hidden/system prompts
- `.weslr` contents
- full massive raw artifact stored in packet
- executable code-as-action
- live tool instructions
- provider/model output claimed as authority
- dangerous procedural domain instructions

These must be blocked, not normalized.

## 20. Output categories
Allowed output categories are limited to:
- terrain map metadata
- motif candidates
- weak-signal labels
- stable-region labels
- unstable-region labels
- noise-region labels
- boundary-region labels
- candidate grammar labels
- operator-like transformation labels
- compression summary
- uncertainty map
- probe suggestions
- invalidation notes
- next experiment labels

## 21. Relationship to `CognitiveResearchRunV1`
`CognitiveResearchRunV1` is shared reporting and safety packet structure only.

For `RAW_SIGNAL_CARTOGRAPHER`, it must be used only as:
- common reporting envelope
- safety boundary carrier
- validation shell
- comparison surface

It must not become:
- the engine kernel itself
- a generic flattening template
- runtime authority
- public claim authority
- provider/tool/search/persistence authority

The engine kernel remains separate and unique.

## 22. Validation principles
The design must validate by ensuring that it:
- preserves strange output metadata
- preserves weak signals instead of deleting them too early
- classifies noise without prematurely discarding it
- allows “unknown terrain” labels
- requires artifact references for massive inputs
- requires summaries instead of raw bulk storage
- blocks private, hidden, secret, procedural, and actionable content
- blocks breakthrough, proof, and public-ready claims

## 23. Safety-frontier rule
Internal exploration may be radical and strange, but this boundary remains:
- metadata-only
- non-executing
- non-public-claiming
- non-authoritative
- non-actionable for sensitive domains
- bounded by denied authority

## 24. Notes on engine individuality
This engine should be able to coexist with later engines such as unintelligible-output analysis, signal-versus-noise, emergence, and mutable-axiom math without being reduced to them.

Its identity is terrain mapping first, explanation second.
