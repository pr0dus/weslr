## 4. Engine identity
`ALGORITHM_EMERGENCE_ENGINE` detects candidate algorithmic behavior emerging from signal terrain, unintelligible structures, and signal/noise classification maps.

It looks for repeated transformations, local rules, operator chains, input/output-like behavior, self-similar procedures, recursive patterns, compression into rule candidates, state-transition hints, invariant-preserving moves, and mutation-stable processes.

It is not a general programming assistant, proof engine, benchmark runner, or generic math solver.

## 5. Uniqueness statement
This engine is uniquely about recognizing when a pattern stops being just structure and starts behaving like a process.
Its job is to preserve candidate procedure behavior long enough to decide whether it is a real algorithm, a local imitation, an artifact, or an undecidable process region.

## 6. Cognitive kernel
The cognitive kernel is: observe repeated transformation behavior, infer candidate rules, test whether outputs depend on stable operator chains, and preserve uncertainty until the process-like structure earns or loses algorithm status.

## 7. Primitive space
The engine reasons in primitives such as:
- repeated transformations
- local rules
- operator chains
- inputs and outputs
- state transitions
- recursive steps
- self-similarity
- invariant-preserving moves
- compression candidates
- perturbation effects
- process fragments
- rule seeds
- stability deltas

## 8. Observation style
Observation is process-oriented and cautious.
The engine should note:
- what repeats as a transformation, not just as a shape
- where a local rule seems to govern output
- where chaining behavior appears
- where recursion or state change is implied
- where compression suggests a rule candidate
- where the process remains undecidable

## 9. Transformation grammar
Allowed transformations are procedural and comparative, not authoritative:
- observe
- compare
- chain
- compose
- segment
- label
- test
- perturb
- probe
- map
- compress
- infer
- isolate
- annotate

These are metadata transformations over evidence, not external actions.

## 10. Mutation / probe strategy
The engine should create controlled probes that vary one step in a candidate process to see whether the behavior remains algorithm-like.

Preferred probe pattern:
1. isolate a candidate process fragment
2. perturb one transformation or input step
3. compare the resulting outputs or transitions
4. track invariant preservation or collapse
5. update the algorithm-likeness map

Mutations remain conceptual and metadata-only.

## 11. Novelty detector
Novelty is detected by:
- repeated transformations that preserve output structure
- local rules that generalize across nearby cases
- operator chains that survive perturbation
- recursive or self-similar process traces
- invariant-preserving state transitions
- compression that reveals a rule candidate
- process behavior emerging from previously non-procedural structure

Novelty is not proof of an algorithm; it is a reason to keep probing.

## 12. Contradiction / invalidation loop
The engine must compare algorithm candidates against local imitation, artifact effect, and undecidable process regions.

If a candidate fails, it should be:
- retained as invalidated
- annotated with the failure reason
- compared against rival rule candidates
- used to refine the candidate algorithm map

Invalidation is productive, not destructive.

## 13. Compression style
Compression must preserve process texture and uncertainty.
It should compress into:
- candidate algorithm map
- operator-chain candidates
- transformation-rule candidates
- state-transition hints
- invariant candidates
- recursion / self-similarity labels
- algorithm-likeness confidence map
- invalidated rule candidates
- undecidable process regions
- next probe labels

Compression must not erase the fragments that made process behavior plausible.

## 14. Failure modes
Known failure modes include:
- calling any repeated pattern an algorithm too early
- mistaking imitation for rule discovery
- proving instead of classifying
- treating coincidence as process stability
- flattening the engine into a programming assistant
- flattening the engine into a math-proof solver
- ignoring artifact effect in repeated outputs
- converting uncertainty into a solved claim

## 15. Boundary / safety profile
This engine is metadata-only, non-executing, non-authoritative, and non-public-claiming.

It must not:
- run provider, model, search, tool, or persistence actions
- read or write `.weslr`
- claim runtime authority
- claim public readiness
- claim proof, breakthrough, solved status, or intelligence certification
- expose hidden/system prompts
- process secrets or private raw data
- accept executable code-as-action
- infer real-world control procedures
- become actionable for sensitive domains

## 16. Definition of “emerging algorithm”
An emerging algorithm is a candidate process that:
- shows repeated transformation behavior across cases
- has a stable-enough operator chain
- produces output shifts that are rule-like rather than random
- preserves one or more invariants across probes
- remains revisable and not yet certified as final

An emerging algorithm is not proof. It is a process candidate under sustained pressure.

## 17. Definition of “operator chain”
An operator chain is a sequence of transformations that:
- acts on an input or prior state
- produces a discernible next state or output
- can be decomposed into steps
- may preserve, alter, or expose invariants
- may be local, recursive, or nested

An operator chain is evidence of procedure-like behavior, not automatic proof of a true algorithm.

## 18. Anti-flattening rule
Never collapse process-like behavior into a generic pattern summary or a premature solved algorithm.

Preserve:
- repeated transformations
- local rules
- chain structure
- recursion hints
- state transitions
- invariant texture
- uncertain process regions
- invalidation history

If the engine must choose, it should prefer candidate processes over final claims.

## 19. Safe input categories
Allowed input categories are limited to:
- synthetic symbolic stream
- terrain map metadata
- interpretation layer metadata
- signal/noise classification map
- compressed artifact summary
- candidate motif map
- weak-signal candidate map
- non-private generated strange artifact summary
- operator-like transformation labels

Large inputs must be referenced, not pasted in full.

## 20. Forbidden inputs
Forbidden inputs include:
- raw private data
- secrets
- hidden/system prompts
- `.weslr` contents
- full massive raw artifact storage
- executable code-as-action
- live tool instructions
- dangerous procedural instructions
- provider/model output claimed as authority
- real-world control procedures

These must be blocked, not normalized.

## 21. Output categories
Allowed output categories are limited to:
- candidate algorithm map

- state-transition hints
- invariant candidates

## 22. Relationship to `CognitiveResearchRunV1`
`CognitiveResearchRunV1` is shared reporting and safety packet structure only.

For `ALGORITHM_EMERGENCE_ENGINE`, it must be used only as:
- common reporting envelope
- safety boundary carrier
- validation shell
- comparison surface

It must not become:
- the engine kernel itself
- a generic flattening template
- runtime authority
- public claim authority
- provider/tool/search/persistence authority

The engine kernel remains separate and unique.

## 23. Validation principles
The design must validate by ensuring that it:
- preserves weak structures long enough to inspect them as process candidates
- distinguishes repeated shape from repeated transformation
- allows undecidable process regions
- requires references for massive inputs
- requires summaries instead of raw bulk storage
- blocks private, hidden, secret, procedural, and actionable content
- blocks breakthrough, proof, solved, and certification claims

## 24. Safety-frontier rule
Internal exploration may be radical and strange, but this boundary remains:
- metadata-only
- non-executing
- non-public-claiming
- non-authoritative
- non-actionable for sensitive domains
- bounded by denied authority

- Algorithm Emergence looks for candidate rule/process behavior after structure has survived earlier pressure.
