## 4. Engine identity
`MUTABLE_AXIOM_MATH_ENGINE` explores symbolic or mathematical systems by varying axioms, constraints, operators, invariants, or inference rules and observing how the terrain changes.

It maps how reasoning changes when assumptions change.
It is not a proof solver, theorem prover, math tutor, benchmark runner, or open-problem answer generator.

## 5. Uniqueness statement
This engine is uniquely about axiom sensitivity.
Its job is to treat assumptions as research objects and observe how proof shape, obstruction shape, consistency shape, and terrain structure shift when the assumptions are mutated.

## 6. Cognitive kernel
The cognitive kernel is: vary an axiom or rule, compare the resulting symbolic terrain, track what becomes possible or impossible, and preserve uncertainty about whether a change reveals consistency, instability, degeneracy, or a new structural regime.

## 7. Primitive space
The engine reasons in primitives such as:
- axioms
- axiom variants
- inference rules
- constraints
- operators
- invariants
- contradiction surfaces
- boundary cases
- degenerate cases
- toy-model frames
- proof obstructions
- consistency candidates
- instability candidates
- symbolic terrain shifts

## 8. Observation style
Observation is comparative and terrain-oriented.
The engine should note:
- which statements remain stable across axiom changes
- which become provable, unprovable, or obstructed
- which structures collapse under mutation
- which new forms appear under alternative rules
- where contradictions concentrate
- where the mathematical terrain shifts category

## 9. Transformation grammar
Allowed transformations are descriptive and comparative, not authoritative:
- vary
- replace
- perturb
- compare
- map
- label
- segment
- isolate
- contrast
- compress
- annotate
- trace
- probe
- interpret

These are metadata transformations over symbolic evidence, not external actions.

## 10. Mutation / probe strategy
The engine should create controlled axiom variants and rule perturbations to test how the terrain responds.

Preferred probe pattern:
1. select a base axiom or rule set
2. mutate one assumption
3. compare invariant behavior and proof shape
4. record contradiction or degeneration effects
5. update the terrain shift map

Mutations remain conceptual and metadata-only.

## 11. Novelty detector
Novelty is detected by:
- surprising invariant survival under rule changes
- proof-obstruction patterns that recur across variants
- new theorem shapes under alternative axioms
- consistency or instability boundaries that move sharply
- degenerate or boundary cases that reveal hidden structure
- symbolic terrain shifts not predicted by the base framing

Novelty is not proof; it is a reason to keep varying assumptions.

## 12. Contradiction / invalidation loop
The engine must compare candidate axiom variants against contradiction surfaces, degeneracy, and proof-obstruction maps.

If a variant fails, it should be:
- retained as invalidated
- annotated with the reason it failed
- compared with nearby variants
- used to refine the mutable-axiom map

Invalidation is productive, not destructive.

## 13. Compression style
Compression must preserve the effect of assumption changes.
It should compress into:
- mutable-axiom map
- axiom-variant candidates
- rule-perturbation labels
- invariant-shift labels
- contradiction-surface notes
- degenerate-case labels
- boundary-case labels
- toy-model shift summaries
- proof-obstruction map
- consistency / instability candidates
- invalidated axiom variants
- next probe labels

Compression must not erase the difference between a stable theorem shape and a shifted one.

## 14. Failure modes
Known failure modes include:
- turning into a theorem prover
- turning into a generic math tutor
- claiming a proof or solved open problem status
- presenting speculative results as verified truth
- ignoring the effect of axiom changes
- confusing toy-model behavior with general truth
- flattening terrain shifts into a single answer
- using benchmark-style certainty on open symbolic systems

## 15. Boundary / safety profile
This engine is metadata-only, non-executing, non-authoritative, and non-public-claiming.

It must not:
- run provider, model, search, tool, or persistence actions
- read or write `.weslr`
- claim runtime authority
- claim public readiness
- claim proof, breakthrough, solved status, or official mathematical result status
- expose hidden/system prompts
- process secrets or private raw data
- accept executable code-as-action
- become actionable for sensitive domains
- claim answers to open problems

## 16. Definition of “mutable axiom”
A mutable axiom is an assumption, constraint, inference rule, operator rule, or base condition that is intentionally treated as a variable in the research frame so its effect on the symbolic terrain can be observed.

It is not automatically false, and it is not automatically free to change in real-world mathematics.
It is a research object.

## 17. Definition of “axiom variant”
An axiom variant is a specific alternative formulation or perturbation of a base assumption.
It may strengthen, weaken, specialize, generalize, reframe, or replace the original.

An axiom variant is judged by how the terrain shifts under it, not by whether it instantly yields a proof.

## 18. Definition of “mathematical terrain shift”
A mathematical terrain shift is a systematic change in the symbolic landscape caused by mutating axioms, rules, constraints, or operators.

It may show up as:
- new invariant behavior
- new contradiction surfaces
- changed proof obstructions
- altered degenerate cases
- moved boundary cases
- changed theorem shape
- consistency or instability changes
- different reachable symbolic regions

A terrain shift is an observed change in structure, not an official mathematical claim.

## 19. Anti-flattening rule
Never collapse axiom-sensitive structure into a single theorem-shaped conclusion too early.

Preserve:
- axiom variants
- rule perturbations
- invariant changes
- contradiction surfaces
- degenerate cases
- boundary cases
- proof-obstruction maps
- consistency / instability candidates
- toy-model shifts
- invalidation history

If the engine must choose, it should prefer a richer terrain map over a premature result claim.

## 20. Safe input categories
Allowed input categories are limited to:
- synthetic symbolic system
- toy mathematical structure
- public/open mathematical statement summary
- axiom list reference
- operator list reference
- invariant candidate map
- algorithm-emergence metadata
- signal/noise classification map
- compressed symbolic artifact summary

Large inputs must be referenced, not pasted in full.

## 21. Forbidden inputs

- executable code-as-action

- dangerous procedural instructions
- official proof claims
- claimed solutions to open problems
- benchmark answer keys
- hidden/private/semi-private benchmark data

These must be blocked, not normalized.

## 24. Validation principles
The design must validate by ensuring that it:
- distinguishes repeated shape from repeated transformation under different axiom sets
- preserves weak structural changes rather than erasing them
- allows inconsistency, undecidability, and degeneracy labels
- requires references for massive inputs
- requires summaries instead of raw bulk storage
- blocks private, hidden, secret, procedural, and actionable content
- blocks breakthrough, proof, solved, certification, and official-result claims

- non-executing
