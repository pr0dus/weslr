## 1. Solver Objective
Design a **bounded 3‑step ARC synthetic solver** that consumes the 20 diagnostic task packets generated by `generate_3_step_pilot_tasks()` (see the task‑schema implementation). The solver must attempt the full pipeline:

```
input → step 1 → intermediate 1 → step 2 → intermediate 2 → step 3 → output
```
for each task, producing the same trace fields required by the diagnostic runner (see Section 5).

The solver is **diagnostic‑first**: the initial implementation may produce failures but must never leak prohibited data or invoke external systems.

---

## 2. Allowed Primitive Execution
The solver may reuse any **existing primitive helper functions** that are already part of the ARC codebase and are already allowed in the 2‑step and single‑step pipelines. Typical primitives include (non‑exhaustive):
- `extract`
- `rotate`
- `recolor`
- `remove_noise`
- `extract_object`
- `fill_region`
- `count_objects`
- `pattern_output`
- `crop_object`
- `transform`
- `place_back`
- `extract_boundary`
- `recolor_boundary`
- `count`
- `isolate_largest`
- `normalize_position`
- `mirror_object`
- `extract_changed_region`
- `crop`
- `count_or_pattern`

If a required primitive is **not** currently implemented, the design must **list the missing primitive contract** (name and required signature) rather than implement it.

## 3. Candidate Generation Strategy
1. **Use the declared `primitive_sequence`** from each task packet – it already specifies the three primitives to execute for that task. No free search over all possible triples.
2. **Parameter Options are bounded**:
   - Each primitive may accept a small, pre‑defined set of dynamic parameters (e.g., `rotation_angle` ∈ {90,180,270}, `colour_map` ∈ {"red","green","blue"}). These options are defined in the task schema (`allowed_dynamic_parameters`). The solver must iterate only over the values listed there.
3. **No shortcuts** – the solver must not use `task_id_shortcut`, `generator_note_shortcut`, or any hidden test‑output fields.
4. **Deterministic per‑task generation** – for a given task the solver produces exactly one candidate (the concrete primitive‑parameter combination defined by the packet).

This strategy prevents combinatorial explosion while still exercising the full 3‑step pipeline.

---

## 4. Intermediate Scoring Policy
For each task the solver computes a **score object** with the following components (each a boolean or numeric weight):
- `step_1_train_fit` – does the output of step 1 match the expected trace export (if any) recorded in the packet?
- `step_2_train_fit` – does the export of step 2 match the packet’s `step_2_exports`?
- `step_3_train_fit` – does the final output match the packet’s expected outcome (if provided – typically absent for pilot, so treated as `True` when no test output is present).
- `intermediate_1_mismatch` – penalty if `intermediate_grid_1_summary` differs from expected.
- `intermediate_2_mismatch` – penalty for step 2 grid mismatch.
- `final_output_mismatch` – penalty if final output deviates from expected (if any).
- `unsupported_primitive` – penalty when a primitive is not available.
- `parameter_drift` – penalty when a parameter value changes between steps beyond allowed ranges.
- `object_identity_loss` – penalty when object IDs are not preserved across steps.

A **simple additive score** can be used:
```
score = (step_1_train_fit + step_2_train_fit + step_3_train_fit) * 1.0
        - unsupported_primitive * 2.0
        - parameter_drift * 1.5
        - intermediate_1_mismatch * 1.0
        - intermediate_2_mismatch * 1.0
        - final_output_mismatch * 2.0
        - object_identity_loss * 1.5
```
Higher scores indicate better compliance; exact matches (all three step fits and no penalties) yield the maximum score.

## 5. Parameter Carry‑over Definition
For each edge the solver must track **which parameters are carried** and **which are dropped**:
- **Edge 1→2 (`carried_parameters_by_edge["1-2"]`)** – parameters explicitly exported by step 1 that are required as inputs by step 2 (e.g., `rotation_angle`, `object_id`).
- **Edge 2→3 (`carried_parameters_by_edge["2-3"]`)** – similarly for step 2 → step 3.
- **Dropped parameters** – any export from a step that is not consumed by the next step.
- **`parameter_origin_by_step`** – map each parameter name to the step where it was first introduced.

The solver must populate these fields in the final trace report for each task.

## 6. Required Trace Fields (per‑task)
The solver’s output trace must contain exactly the same keys as the diagnostic runner:
- `step_1_exports`
- `step_2_imports`
- `step_2_exports`
- `step_3_imports`
- `carried_parameters_by_edge`
- `dropped_parameters_by_edge`
- `parameter_origin_by_step`
- `intermediate_grid_1_summary`
- `intermediate_grid_2_summary`
- `failure_step`
- `failure_reason`
- `sequence_visibility_reason`
- `leakage_flags` (all must be `False`)

If a task fails early, later fields may be empty but must still be present with appropriate default values.

---

## 7. Failure Categories (exhaustive list)
The solver must classify failures into one of the following **canonical categories**:
1. `unsupported_primitive` – primitive not present in the codebase.
2. `missing_parameter` – required dynamic parameter not supplied.
3. `unstable_parameter` – parameter value outside allowed range.
4. `parameter_drift` – same parameter changes value between steps unexpectedly.
5. `object_identity_loss` – object identifiers are not preserved across steps.
6. `intermediate_1_mismatch` – step 1 intermediate grid does not match expectation.
7. `intermediate_2_mismatch` – step 2 intermediate grid mismatch.
8. `final_output_mismatch` – final output does not match expected (if an expectation exists).
9. `ranking_blocked` – candidate cannot be ranked due to missing metadata.
10. `composition_failure` – primitive composition invalid (e.g., incompatible shapes).
11. `leakage_blocked` – any leakage flag would need to be set to `True` (never allowed).
12. `unknown` – any unexpected error not captured above.

Only a **single primary category** is recorded per task; additional details can be placed in `failure_reason`.

---

## 8. Score Policy for the 20‑Task Pilot
- **Exact rate** = `exact / 20` where `exact` counts tasks where all three step fits are `True` and no penalties apply.
- **Capability thresholds**:
  - **Minimal**: 17/20 exact = **85%**
  - **Strong**: 18/20 exact = **90%**
  - **Very strong**: 19/20 exact = **95%**
  - **Clean**: 20/20 exact = **100%**
- The **first solver run** is allowed to fall below 85%; it will be treated as a **diagnostic run** provided:
  - No leakage flags are set.
  - No crashes or unhandled exceptions.
  - No regression against the 2‑step or single‑step baselines.
  - All failure categories are clearly reported.
- Only when the solver reaches **≥ 85% exact** and satisfies the above safety conditions may it be labelled “minimally capable”.

## 9. Baseline Preservation
The solver design must **not modify** any of the existing baseline statistics:
- 2‑step 80: `77 / 3 / 0 / 0`
- 2‑step 40: `39 / 1 / 0 / 0`
- Single‑step canonical: `114 / 6 / 0 / 0`
- All static‑local real‑evidence replay milestones remain unchanged.
The solver operates on a **separate module** and writes only its own trace report; it never touches the baseline files.

---

## 10. Leakage Boundaries (hard constraints)
The solver **must never**:
- Access or emit `expected_test_output` values.
- Use hidden/private ARC data or ARC‑AGI participation/score/leaderboard fields.
- Wire any `candidate_output_surface` or final‑answer generation.
- Perform external network calls, provider/model invocations, or file writes outside its own trace output.
- Interact with runtime/chat wiring mechanisms.
- Write to any `.weslr` location.
All `leakage_flags` in the trace must remain `False`.
