# WESLR Ranked Response Shadow Evaluation Report V1

## SECTION 1 — PURPOSE

This document defines the design-only report surface for future WESLR ranked response shadow evaluation results.

The report surface is intended to summarize helper-only shadow scenario results so reviewers can inspect readiness of ranked state-grounded response formation helpers before any implementation of a report generator, runtime path, or user-facing answer path.

The future report should help reviewers understand:

- scenario coverage
- pass/fail counts
- category-level outcomes
- selected labels
- rejection labels
- evidence and provenance behavior
- governance-needed cases
- final-answer contract metadata
- safety boundary confirmations
- no raw content retention
- no official claims

Layer: `WESLR_CANON_ALIGNMENT / design-only`.

This document does not implement a report helper, report runner, response generator, scenario change, helper change, runtime change, persistence path, or final-answer path.

## SECTION 2 — CLAIM BOUNDARIES AND NON-GOALS

The future ranked response shadow evaluation report is internal shadow metadata only. It must not present results as product readiness, public certification, official benchmark performance, Turing-test result, IQ result, consciousness evidence, sentience evidence, or deployment approval.

OCC/OpenClaw is the construction and inspection tool used to inspect and modify this repository when instructed. OCC/OpenClaw is not part of deployed WESLR and must not be described as WESLR in the report surface.

Non-goals:

- no runtime behavior changes
- no `weslr/chat_responder.py` edits
- no ranked shadow helper changes in this design lane
- no ranked scenario changes in this design lane
- no report generator implementation
- no report runner implementation
- no ChatResponder, `respond_chat()`, or `generate_chat()` calls
- no prompt execution
- no model, search, or advisor provider calls
- no candidate prose generation
- no final user-facing answer generation
- no persistence
- no `.weslr` writes
- no raw prompt storage
- no raw response storage
- no raw final answer storage
- no hidden prompt or answer key handling
- no feature flag enablement
- no defaults changes
- no network calls
- no subprocess calls
- no voice, prosody, or TTS work
- no numeric official scoring
- no official benchmark, Turing, IQ, certification, product-readiness, consciousness, or sentience claim

The report may use qualitative internal readiness labels. Those labels are not official evaluation claims and must remain bounded to the shadow helper/scenario lane.

   - report type
   - schema version
   - repo HEAD metadata if provided

   - generated-by helper name
   - non-runtime / non-official / metadata-only flags

2. **Scenario coverage summary**
   - scenario count
   - category count
   - required category coverage status
   - unique scenario ID status
   - missing categories, if any
   - duplicate IDs, if any

3. **Pass/fail summary**
   - passed count
   - failed count
   - blocked count when validation cannot safely render
   - aggregate report label

4. **Category result table**
   - one row per category or scenario

10. **Safety boundary summary**

    - no persistence performed

11. **Gaps/risks**
    - missing categories

## SECTION 6 — CATEGORY RESULT TABLE DESIGN

Future report helpers should render a category-level table with this shape:

| category | scenario_id | scenario_name | pass/fail | selected_label | rejected_count | key rejection labels | evidence/provenance behavior | governance needed? | final-answer generated? | notes |
|---|---|---|---|---|---:|---|---|---|---|---|
| `context_variation` | `rrsev1_context_variation_001` | metadata-only name | pass | `strong_fit` | 1 | `weak_context_fit` | provenance optional/clear | no | no | metadata only |

Column policy:

- `category`: required category label.
- `scenario_id`: stable synthetic ID only.
- `scenario_name`: short synthetic scenario name only.
- `pass/fail`: scenario result status or validation status.
- `selected_label`: qualitative selected label only.
- `rejected_count`: count only.
- `key rejection labels`: bounded label list only.
- `evidence/provenance behavior`: concise labels such as `evidence_satisfied`, `evidence_missing`, `provenance_clear`, `provenance_missing`, `evidence_boundary_exercised`, or `provenance_boundary_exercised`.
- `governance needed?`: `yes`, `no`, or `expected_yes`.
- `final-answer generated?`: must be `no` for a valid report.
- `notes`: short metadata-only notes, never raw content.

The table must not include raw prompts, raw responses, final answer text, hidden prompts, answer keys, private content, candidate prose, model output, or official claims.

## SECTION 7 — AGGREGATE LABELS

Future report helpers should derive qualitative aggregate labels only.

Recommended aggregate report status labels:

- `shadow_report_clean` — all required categories present, all scenarios pass, safety flags clear, no governance follow-up required beyond expected ordinary review.
- `shadow_report_clean_with_minor_gaps` — all safety boundaries clear and no failures, but minor non-blocking gaps exist such as compact category evidence or wording improvements.
- `shadow_report_needs_followup` — one or more scenario failures, missing categories, unexpected rejection labels, unclear governance labeling, or evidence/provenance ambiguity requires follow-up before helper implementation advances.
- `shadow_report_blocked` — forbidden raw content, unsafe flags, actual side effects, runtime wiring, final answer generation, official claims, or invalid report input prevents safe rendering.
- `needs_governance_review` — governance-required candidates or rejection labels are present and should be reviewed as governance outcomes, especially if not expected by the scenario.
- `evidence_boundary_exercised` — at least one scenario tested evidence requirement, insufficiency, or evidence-preserving fallback.
- `provenance_boundary_exercised` — at least one scenario tested provenance requirement, missing provenance, or attribution boundary.
- `non_cannedness_boundary_exercised` — at least one scenario tested demotion or rejection of generic, keyword-only, or template-like candidates.
- `runtime_integration_not_authorized` — always present for this report lane unless a separate governance decision explicitly changes the lane.

Aggregate labels should be derived from metadata and should not be numeric official scores.

## SECTION 8 — GOVERNANCE ESCALATION REPORTING

Governance escalation reporting must distinguish candidate-level metadata, rejection labels, and aggregate report status.

Required handling:

1. Candidate-level `requires_governance=true` means a synthetic candidate claims it requires governance before proceeding.
2. Rejection labels such as `governance_required`, `needs_governance`, or `not_authorized` may indicate the helper correctly refused to select a candidate without governance.
3. Aggregate `needs_governance_review` should be present when governance-required metadata appears in any scenario result.
4. Governance need must not be treated as a failure when the scenario expected escalation or rejection.
5. Governance need should be treated as follow-up or blocked only when it is unexpected, hidden, missing from labels, or paired with unsafe selection.

Recommended display pattern:

- `governance_needed_count`: number of scenarios where governance was required or rejected for governance.
- `governance_expected_count`: number of scenarios where governance need was expected.
- `governance_unexpected_count`: number of scenarios where governance need was unexpected.
- `governance_aggregate_label`: `needs_governance_review` when any governance-required result exists.
- `governance_status`: `expected_boundary_exercised`, `unexpected_followup_needed`, or `blocked`.

A governance-needed result is a safety signal, not an automatic failure.

## SECTION 9 — EXTERNAL-HELP NEGATIVE METADATA DISTINCTION

The report must clearly distinguish between candidate-level external-help negative metadata and actual external side effects.

Candidate-level metadata examples:

- `requires_model_call=true`
- `requires_search_call=true`
- `requires_advisor_call=true`

Those fields may be valid synthetic negative-test metadata when the expected behavior is rejection, demotion, or `not_authorized` labeling.

Actual side-effect flags must remain false:

- `model_call_made=false`
- `search_call_made=false`
- `advisor_call_made=false`

Report wording should say:

- Candidate-level external-help requirements are allowed only as metadata for negative tests.
- Actual model/search/advisor calls are not allowed.
- A valid report can show rejected candidates that would have required external help while simultaneously confirming no external help was actually called.
- If actual side-effect flags are true, the report must be `shadow_report_blocked` and should refuse normal rendering.

This distinction prevents false alarms while preserving the hard boundary against model/search/advisor side effects.

- full conversation text

- official claim markers
- consciousness/sentience markers
- OCC-as-WESLR markers
- runtime wiring markers
- feature flag enablement markers
- network/subprocess call markers
- persistence or `.weslr` write markers

Required safe-report confirmations:

- `raw_prompt_retained=false`
- `raw_response_retained=false`
- `final_answer_generated=false`
- `final_answer_text_present=false`
- `model_call_made=false`
- `search_call_made=false`
- `advisor_call_made=false`
- `persistence_performed=false`
- `runtime_wired=false`
- `feature_flags_enabled=false` when such metadata is present
- `official_evaluation_claimed=false`

If any forbidden raw-content field or unsafe side-effect flag is present, the report should emit only a blocked validation summary with safe labels and counts, not the offending content.

Markdown rendering should redact or omit unsafe keys and should prefer refusing to render over rendering unsafe content.

## SECTION 11 — RELATIONSHIP TO NATIVE HELPERS

Ranked response shadow reports evaluate ranked response formation scenarios: state frame metadata, candidate metadata, ranking labels, rejection labels, self-check metadata, final-answer contract metadata, and safety flags.

Native dry-slice helpers remain separate structural previews. They can inform architecture, but they are not final-answer authority and do not authorize runtime wiring.

Relationship boundaries:

- ranked shadow scenario reports are not native helper reports
- native helper overlap may be mentioned as metadata-only category coverage
- neither ranked shadow reports nor native dry-slice helpers generate final user-facing answers
- neither authorizes `weslr/chat_responder.py` changes
- neither authorizes model/search/advisor calls
- neither authorizes runtime integration
- neither is public evaluation evidence

The `native_helper_overlap` category should confirm separation, not merge authority.

## SECTION 13 — RISKS AND GUARDRAILS

Risks:

- report tables could accidentally look like official scoring
- governance-required scenarios could be mislabeled as failures
- candidate-level external-help negative metadata could be confused with actual side effects
- native helper overlap could be mistaken for final-answer authority
- scenario names or notes could drift into raw prompt/response content
- markdown rendering could leak forbidden fields if validation is weak
- report summaries could imply runtime readiness or product readiness

Guardrails:

- qualitative labels only
- no numeric official scoring
- count/status/label orientation
- strict raw-content rejection
- blocked rendering mode for unsafe input
- explicit non-runtime and non-official flags
- explicit external-help metadata vs side-effect distinction
- explicit governance aggregate labeling
- explicit native helper separation
- explicit `runtime_integration_not_authorized` label
- no persistence unless a later implementation explicitly writes a review artifact under governance
