# WESLR Self-Use Provenance Architecture Design V1

## Status

- design_only
- self_use_provenance_architecture
- execution_allowed = false
- official_score_claimed = false
- no_behavior_change
- no_runtime_integration

## Purpose

Design a shared architecture so WESLR can explain its own outputs, suggestions, observations, advisor reviews, voice/proactive utterances, and capability guidance.

This design is a specification boundary only. It defines a future common provenance surface and authority vocabulary; it does not implement routers, change chat/runtime behavior, write queues, wire voice/proactive outputs, call models, mutate memory, or authorize any public behavior change.

## Core problem

WESLR has many separate provenance/suggestion/capability systems, but no unified surface that answers:

- who/what generated this?
- why was it generated?
- what triggered it?
- what authority does it have?
- was an LLM involved?
- what should happen next?

Existing bricks include identity and self-model surfaces, capability registry/router/welcome surfaces, decision provenance and source modules, audit/trace/proposal traceability, voice/ambient/proactive layers, suggestion/proposal/review queues, LLM Advisor Mode and advisor review queue infrastructure, state/status/checkpoint modules, and memory/continuity modules. The missing shared brick is a unified provenance and authority envelope that all of those surfaces can use.

## Unified output provenance envelope

Future WESLR outputs should be able to attach or reference a unified output provenance envelope. The envelope is metadata about an output; it is not permission to execute and does not make the output true.

Proposed future fields:

- `output_id`: stable identifier for the rendered output, utterance, suggestion, advisor summary, guidance item, or observation.
- `generated_by`: primary generating subsystem ID, human operator, or reviewed source.
- `source_modules`: ordered list of subsystem IDs that contributed evidence, templates, suggestions, or render decisions.
- `trigger`: short deterministic explanation of the event, user query, timer, review signal, diagnostic, or operator action that caused generation.
- `trigger_type`: safe category such as `user_query`, `operator_command`, `observed_event`, `internal_check`, `advisor_review`, `capability_guidance`, `voice_event`, or `unknown`.
- `input_channel`: source channel or lane, such as chat, CLI, review queue, voice gateway, state scan, or advisor packet.
- `output_channel`: destination channel or lane, such as chat, CLI, voice, proactive surface, proposal queue, review queue, or design doc.
- `authority_level`: one of the safe authority levels defined below.
- `truth_class`: bounded classification such as `observed`, `inferred`, `proposal`, `operator_decision`, `teaching_example`, `unverified_external`, or `unknown`.
- `confidence`: numeric or categorical confidence in the provenance metadata and trigger classification, not a truth/soundness score.
- `llm_assisted`: whether an LLM contributed to wording, review, extraction, or suggestion generation.
- `advisor_assisted`: whether LLM Advisor Mode or an advisor review record contributed.
- `operator_review_required`: whether the output requires explicit operator review before adoption, execution, persistence, policy use, or public claim.
- `raw_sensitive_content_stored`: whether raw sensitive content was stored; default should be false.
- `memory_write_performed`: whether a memory mutation happened; default should be false and must not be hidden.
- `queue_write_performed`: whether a queue mutation happened; default should be false and must not be hidden.
- `runtime_action_performed`: whether runtime behavior, config, scheduling, daemon, router, voice, or chat behavior changed; default should be false and must not be hidden.
- `created_at`: timestamp generated by the owning deterministic subsystem.
- `trace_refs`: links to audit, trace, proposal, checkpoint, or diagnostic records that support the attribution.
- `related_queue_item_ids`: related suggestion/proposal/review queue item identifiers, if any.
- `related_advisor_review_ids`: related advisor review identifiers, if any.

The envelope should let WESLR say what produced an output, which systems contributed, which boundary applies, whether LLM/advisor assistance occurred, whether any writes/actions occurred, and what trace record supports the answer.

## Authority levels

Safe authority categories:

- `system_fact`: deterministic fact about known WESLR code, configuration, schema, or documented system status, backed by inspection or registry data.
- `observed_event`: event WESLR directly observed through logs, traces, state checkpoints, user messages, or tool output.
- `internal_diagnostic`: diagnostic interpretation produced by WESLR-owned checks; useful but not external truth.
- `suggestion`: non-authoritative next-step idea requiring user/operator judgment before action.
- `advisor_proposal`: non-authoritative proposal input originating from or assisted by LLM Advisor Mode.
- `voice_surface`: voice/proactive rendering or utterance layer output; it must still carry its source and trigger.
- `teaching_explanation`: educational explanation or synthetic teaching lane output; not proof authority or answer selection.
- `operator_decision`: explicit operator approval/rejection/deferral record.
- `unknown`: provenance or authority is incomplete; WESLR should say it is unknown rather than guessing.

## Source registry concept

A future provenance source registry should map subsystem IDs to deterministic metadata. This registry is the lookup layer for answering “which part of you generated this?” and for deciding which systems may emit which kinds of output.

Each registry entry should include:

- human-readable description
- authority boundary
- allowed outputs
- forbidden outputs
- whether LLM-assisted
- whether operator review is required
- related tests/docs

Example subsystem IDs:

- `capability_registry`
- `capability_welcome_surface`
- `proactive_suggestions`
- `ambient_voice_loop`
- `voice_gateway`
- `llm_advisor_mode`
- `advisor_review_queue`
- `synthetic_teaching_lane`
- `state_checkpoint`
- `memory_capture`
- `proposal_traceability`

The registry should not grant authority by itself. It should describe boundaries so WESLR can attribute outputs and refuse unsupported authority claims.

## Required self-use query surfaces

Future WESLR should provide deterministic self-use answers for these user/operator questions:

- “what can you do?” — answer from capability registry and guidance metadata, separating live, read-only, design-only, experimental, and internal-only capabilities.
- “what did you notice?” — answer from observed events, diagnostics, state checkpoints, review suggestions, and provenance-backed observations, not from vague intuition.
- “who said that?” — answer from provenance records identifying source subsystem, operator, advisor model/provider, or unknown.
- “why did you suggest this?” — answer from trigger, trigger_type, source_modules, trace_refs, and authority_level.
- “which part of you generated this?” — answer from generated_by plus source registry descriptions and boundaries.
- “what should we improve next?” — answer from review/proposal queues, missing coverage diagnostics, capability gaps, and operator-visible suggestions.
- “where can this take me?” — answer from capability guidance: possible next capabilities, staged workflows, safe experiments, and required approvals.
- “was an LLM involved?” — answer from llm_assisted, advisor_assisted, related_advisor_review_ids, model/provider traces where available, or unknown if not recorded.

If a provenance record is missing, WESLR should say the attribution is missing or unknown and may create a review suggestion later; it should not infer a convenient answer.

## Voice/proactive attribution

Future rule: every proactive/voice utterance must have an attribution record before it is treated as WESLR-owned output.

Every proactive/voice attribution record should include:

- source subsystem
- trigger
- model/provider if LLM-assisted
- timestamp
- confidence
- whether WESLR-owned or advisor/LLM-assisted
- what log/trace record supports it

For “who said that?”, WESLR should answer from provenance records, not guess.

Voice/proactive outputs should be blocked, downgraded, or rendered as unattributed/unknown if the required attribution record is absent. proactive/voice utterances require attribution. Voice/proactive utterances must not silently hide LLM assistance, advisor assistance, queue writes, memory writes, or runtime actions.

## Capability guidance surface

The future guidance layer should answer more than “what can you do?”. It should also support:

- “what should I try next?”
- “where can this take me?”
- “which capability fits this goal?”
- “which capability is experimental/internal-only?”

Capability guidance should combine the capability registry, welcome surface, source registry, state/status data, and operator-approved documentation. Guidance must remain suggestion, not authority. It should not execute capabilities, select answers, claim truth/soundness, mutate memory, write queues, call advisors, or change runtime behavior by itself.

Guidance records should expose status labels such as live, read-only, design-only, staging-only, experimental, operator-required, internal-only, and deprecated. The user should be able to see whether a suggestion is safe to try now or requires an explicit operator decision.

## Self-review and suggestion integration

Future WESLR self-use may create review suggestions when deterministic checks notice gaps such as:

- capability gap noticed
- stale advisor template noticed
- unsupported gap trend noticed
- missing provenance record noticed
- voice attribution missing
- new capability lacks user guidance

These should become review/proposal queue items, not automatic changes. A self-review suggestion should carry its own provenance envelope, state why it exists, identify the subsystem that noticed it, mark `operator_review_required = true`, and avoid hidden queue writes. If queue writing is later approved, queue writes must be explicit, traced, and visible through `queue_write_performed` and related queue IDs.

## LLM Advisor integration

This capability can later be improved through LLM Advisor Mode, while preserving WESLR authority boundaries.

Advisor review may help with:

- advisor reviews provenance coverage
- advisor suggests missing source registry entries
- advisor suggests tests
- advisor reviews wording risk
- advisor reviews capability guidance
- advisor reviews “who said that?” behavior

Hard boundary: LLM advisor output is non-authoritative proposal input only. It cannot become truth, memory, runtime behavior, or policy without validation and operator approval.

Advisor-assisted improvements should be converted into WESLR-owned proposal candidates, test candidates, design notes, or review queue items. Advisor records must preserve model/provider identity and must not hide model assistance behind WESLR-owned authority.

## Safety boundaries

The architecture forbids:

- answer selection
- truth/soundness authority
- official score claims
- hidden LLM authority
- hidden memory mutation
- hidden queue writes
- hidden runtime actions
- raw sensitive content storage by default
- provenance guessing
- voice/proactive utterances without attribution
- advisor output as final authority

Additional safety rules:

- Unknown provenance must remain unknown until supported by records.
- Confidence describes metadata quality, not proof soundness or official score.
- The envelope must expose whether writes/actions occurred; it must not perform those writes/actions.
- LLM/advisor assistance must be visible when known.
- Operator decisions must be separated from suggestions and advisor proposals.

## Non-goals

- no implementation in this phase
- no unified router
- no voice wiring
- no queue writes
- no runtime/chat integration
- no model calls
- no daemon/cron
- no memory mutation
- no public behavior change

This document does not create schema modules, persistence helpers, queue adapters, daemon loops, cron jobs, voice routing, chat routing, advisor calls, capability execution, parser/normalizer/solver changes, MCQ/scoring behavior, OpenClaw configuration changes, or TIA/C#/industrial changes.
